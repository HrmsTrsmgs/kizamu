# テストコードの記述方針

この文書は、Kizamuのテストの可読性を保つ記述方針を定義する。
「可読性の優先順位」と「検証対象を直接アサーションへ渡す」は言語共通とし、その他のvar・変数・Fluentな検証句の方針はC#/.NETを対象とする。
Fluentな検証句はAwesomeAssertionsで記述する。FluentAssertions由来の記述方針も引き継ぎ、採用ライブラリの方針は `ai-instructions/csharp.md` を参照する。

## 可読性の優先順位

テストは可読性を最優先し、何を検証し何を期待するかを仕様として一読できる記述を選ぶ。短さ、既存記法の維持、設定変更の手間よりも読みやすさを重視する。ライブラリや記法も実際のテストで比較して選び、検証内容・意味は維持する。

## 検証対象を直接アサーションへ渡す

使用中のAssertに、等価性・包含・件数・例外などを直接検証する機能がある場合は、その機能へ対象の値やコレクションを渡す。判定結果を不要に `true`／`false` へ潰さず、テスト本体から何と何を比較しているかを読めるようにする。

Vitestが公開するChaiの `should` での例:

```ts
// 判定結果だけを検証しない。
expect(record.startedAt.equals(開始時刻)).toBe(true)

// 対象 → should → 期待すること、の順で日時点を直接比較する。
record.startedAt.should.deep.equal(開始時刻)
```

`should` はテスト環境内だけで有効化する。基本の初期化と型宣言は [共通のテスト初期化](../tests/should.mts) に集約し、各テストプロジェクトから読み込む。JSDOMのDOMノードは別系統のオブジェクトであるため、[Reactのテスト初期化](../tests/frontends/react/test/setup.ts) でも標準の `should` getterを登録する。

`null`／`undefined` には直接 `.should` をつなげられないため、nullableなプロパティは親オブジェクトから `should.have.property(...)` などで検証する。画面検索の不在確認には標準の `should.not.exist(...)` を使う。optional chainingで検証を飛ばしたり、非nullアサーションで回避したりしない。

検証対象自体が真偽値のプロパティ・戻り値である場合や、適切な直接検証のAssertがない場合は、真偽値による検証を許容する。テストの意味を弱めたり、この規則のためだけに独自Assertやヘルパーを無理に増やしたりしない。`toBeTruthy()` やChaiの真偽値検証などへ表記だけを替えても、この原則を満たしたことにはならない。

## varの使用方針

ローカル変数は原則として `var` を使用する。

次の場合は具体型を明記してよい。

* フィールド宣言
* メソッドやプロパティの公開シグネチャ
* ラムダ式の代入先として型が必要な場合
* 具体型そのものをコンパイル時に確認するテスト
* `var` では意図が著しく分かりにくくなる場合

例外検証のラムダも原則として `var` で受ける。デリゲート型そのものを示す必要がある場合や、戻り値を持つ処理、非同期処理を明示的に区別したい場合は、そのテストで必要な型を選ぶ。

共有するテスト対象のフィールドは具体型を明記する。

## 一時変数を作る基準

一時変数は、単に長い式へ英語名を付けるためには作らない。次のいずれかに該当する場合に作る。

* 同じ値を複数回使用する
* 複数の検証で同じ対象を使用する
* 列挙や評価を一度だけに固定する
* 例外アサーションを一度だけ実行して複数プロパティを検証する
* 式の一部が独立した概念を表す
* デバッグ時に途中結果を観察する価値が高い

例外について複数の情報を確認する場合は、例外オブジェクトではなく例外アサーションを変数へ受ける。`Which` は後続の `Should()` へつなぐために使い、変数へ受けない。

## Fluentなアサーションとnull検証

nullableな値を検証した後に同じ値を続けて使う場合は、まず `Should().NotBeNull()` で仕様として非nullを確認する。確認後の値を使うためだけに、`!`、`?? throw`、`Which` を追加しない。

`Which` は、例外検証や型検証などでAwesomeAssertionsのチェーンとしてさらに検証を続ける場合に使う。nullable解析を外すための一時変数化には使わない。

## Fluentな検証句の改行

`Should()` と最終アサーションは原則として同じ行に置く。AwesomeAssertionsは英文に近い検証句として読むため、`Should()` だけを単独行にして述語を分断しない。

`Which`、検証対象の短いプロパティ、`ToString()` なども、一続きの句として読める場合は無理に縦へ分割しない。検証対象を作るチェーンは、声に出して読んだときの区切りや意味の切れ目で改行してよいが、`Should()` の前で改行すること自体をルールにはしない。

期待値が長い場合は、`Should()` とアサーション名ではなく、引数側を改行する。

## 一時変数を作らない基準

一度しか使用せず、右辺の式がそのまま意味を表している場合は、直接アサーションへつなげる。特に、次のような一般名が右辺以上の情報を加えない場合は原則としてインライン化する。

```text
actual
result
value
data
item
object
```

同じ値を複数回使う場合や、評価回数を固定する必要がある場合は一時変数を使用してよい。インライン化によって式が読みにくくなる場合は、短さを優先しない。

## 変数名を付ける場合

一時変数を作る場合は、可能であれば対象の意味を表す名前にする。単に処理結果であることしか示さない名前より、対象の役割を示す名前を優先する。

テスト対象となるオブジェクトを変数で受ける必要があり、型名や種類名をそのまま変数名にするだけなら `tested` とする。ただし、名前を考えるために不自然な抽象化を追加しない。

英語の変数名を増やすこと自体を可読性向上とはみなさない。日本語識別子の方が仕様として読みやすい場合は、日本語識別子を使用してよい。

## テスト対象の共有

テストクラス全体の前提になる対象や、多くのテストで同じ初期化が必要な対象は、`readonly` フィールドとしてテストクラスのコンストラクターで初期化する。

一つのテストでしか使用しない値は、原則としてそのテストメソッド内に置く。共通化のためだけに定数、フィールド、ヘルパーメソッドを増やさない。

## 期待値の扱い

期待値を一度しか使用せず、長さが許容範囲であればアサーション内へ直接書く。次の場合だけ、期待値を変数へ分離する。

* 複数の検証で使用する
* 期待値が非常に長く、テストの観測対象が見えにくくなる
* 期待値自体が独立した概念を表す
* 実際値と期待値を別々にデバッグする必要がある

単に `expected` という名前を付けるだけでは、原則として分離する理由にならない。

## 既存テストへの適用

既存テストを整理するときは、次を守る。

* 明示型のローカル変数を、必要がなければ `var` へ変更する
* 一度しか使わない `actual`、`result` などをインライン化する
* 同じ列挙を複数回行っている場合は、一度配列などで受ける
* 同じ例外の複数プロパティを検証する場合は、例外アサーションを変数へ受ける
* テストクラス全体の前提になる対象は `readonly` フィールドへ置く
* 一つのテストでしか使わない値はローカルへ戻す
* 変数削減によって式が過度に長くなる場合は無理にインライン化しない
* 振る舞いやテストの意味は変更しない
* テスト名、Skip状態、Skip理由は変更しない
* 列挙回数や評価タイミングを意図せず変更しない

## 基本原則

一時変数は、英語名を追加するためではなく、評価回数の固定、検証対象の共有、概念境界の明示、デバッグ可能性の向上に効果がある場合に使用する。

これらの効果がない場合は式を直接読める形を優先するが、インライン化を目的化しない。短さよりも、テストがどの振る舞いを検証しているかを明確に読めることを優先する。
