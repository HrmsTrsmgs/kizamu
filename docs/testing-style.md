# テストコードの記述方針

共通の設計・可読性・準備の判断基準は、個人共通AGENTS（未導入時は [参照版](ai-instructions/common.md#テストの設計と準備)）に従う。

## 可読性の優先順位

共通AGENTSの「テストの設計と準備」を参照する。ライブラリや記法は実際のテストで比較し、検証の意味を維持する。

## テストの準備と補助メソッド

準備の抽出・命名・本文に残す条件は共通AGENTSに従う。Kizamuでは次の技術別の補足を使う。

* 今回確認する操作と期待結果は本文で読めるようにする。Moqの呼び出し検証は後述の方針に従い、検証処理を補助メソッドへ外出ししてよい。準備の成立確認を補助メソッド内で行う場合も、主題の検証をそこへ混在させない。

* 共通する対象・依存オブジェクトの生成と初期化は、まずテストごとの共通準備へまとめる。C#／xUnitではテストクラスのコンストラクター、TypeScript／Vitestでは `beforeEach` を使う。共通準備で扱えないテスト固有の前提は、必要に応じて補助メソッド・関数へ切り出す。
* 個別の準備から複数の結果を返す場合は、C#の名前付きタプルやTypeScriptのオブジェクトを使い、呼び出し側で分解して受ける形を検討する。共通準備をコンストラクター／`beforeEach` へまとめたうえで、テスト固有の準備に適用する。

## Moqの設定と呼び出し検証

テスト本文では、モックの構文よりも前提・操作・期待結果を読み取れることを優先する。Moqの `Setup`、`SetupGet`、`Verify` は原則として、意味が分かる名前の補助メソッドへ外出しする。

* 補助メソッド名は、設定する状態や確認する操作を表す。
* `Times`、設定する値、検証する引数など、結果を左右する条件や期待値は補助メソッドの引数として本文に示す。呼び出し回数や期待値を補助メソッド内へ隠さない。
* 検証自体は補助メソッドが行ってよい。テスト本文には、何をどの条件で確認するかが補助メソッド名と引数から読める呼び出しを残す。
* 補助メソッドはまずテストクラスの近くに置き、不要な汎用化やDSLを作らない。

## テスト準備の一時変数

テスト対象や依存オブジェクトの準備でも、値を一度だけ次の生成や呼び出しに渡すための一時変数は原則として作らず、使用する場所に直接記述する。複数回使用する値の共有、評価回数や順序の固定、非同期処理の制御、検証や可読性に意味がある場合は変数を使用してよい。インライン化によって評価のタイミングやテストの意味を変えず、短さだけを優先しない。

## 検証対象を直接アサーションへ渡す

共通AGENTSの直接Assertの原則に、以下のTypeScript固有の記法を適用する。

Vitestが公開するChaiの `should` での例:

```ts
// 判定結果だけを検証しない。
expect(record.startedAt.equals(開始時刻)).toBe(true)

// 対象 → should → 期待すること、の順で日時点を直接比較する。
record.startedAt.should.deep.equal(開始時刻)
```

Domainクラスの種類も保証する構造比較では、期待値にクラスのインスタンスを置き、配列や親オブジェクトごと `should.toStrictEqual(...)` で比較する。`should.deep.equal(...)` は同じプロパティを持つplain objectも等しいと扱うため、クラスの保証には使わない。`toStrictEqual` は `undefined` のキーや疎配列も区別するので、変更前後の検証内容を確認し、日時・期間などの値比較やJSONの比較を一律に置き換えない。

`should` はテスト環境内だけで有効化する。基本の初期化と型宣言は [共通のテスト初期化](../tests/should.mts) に集約し、各テストプロジェクトから読み込む。JSDOMのDOMノードは別系統のオブジェクトであるため、[Reactのテスト初期化](../tests/frontends/react/test/setup.ts) でも標準の `should` getterを登録する。

`null`／`undefined` には直接 `.should` をつなげられないため、nullableなプロパティは親オブジェクトから `should.have.property(...)` などで検証する。画面検索の不在確認には標準の `should.not.exist(...)` を使う。optional chainingで検証を飛ばしたり、非nullアサーションで回避したりしない。

真偽値を直接検証する例外と、記法だけを置換しない原則は共通AGENTSに従う。

## CSharp共通記法

共通Skill `csharp-conventions` のテスト記述を使う場合は、ここから先を重ねて読まない。採用ライブラリは [C#の補足](ai-instructions/csharp.md#プロジェクトの補足) を確認する。

### 変数を作る理由

ローカルと例外検証のラムダは原則 `var`。フィールド、公開シグネチャ、推論できないラムダ、具体型自体を示すAPI例など、型を明記する意味がある場合は具体型を使う。戻り値・非同期処理の違いを示す必要があれば適切なデリゲート型を選び、`var` で意図が著しく読みにくくなる場合も具体型を許容する。

一時変数は次のいずれかに意味がある場合に作る。

- 複数回使う値・検証対象を共有する。
- 列挙や評価、例外アサーションの実行を一度に固定する。
- 独立した概念を示す。
- デバッグで途中結果を観察する価値がある。

単に `actual`、`result`、`value`、`expected` と名付けても右辺以上の情報が増えなければ、直接検証へつなぐ。短さのために長すぎる式へインライン化することも目的にしない。

```csharp
// 値を受けるだけの中間変数は不要です。
tested.Value.Should().Be(expected);

// 一度の評価結果を複数の観点で使うときは、変数に意味があります。
var rows = tested.ToArray();
rows.Select(it => it.Id).Should().Equal(1, 2, 3);
rows.Select(it => it.Name).Should().Equal("a", "b", "c");
```

これらは記述方針の模式例であり、具体的な型やAPIの存在を前提にするものではない。

変数が必要なら役割の名前を優先し、テスト対象の型名を言い換えるだけなら `tested` とする。命名のための不自然な抽象化は作らない。日本語識別子の方が仕様を読みやすくできるなら使う。

### 準備とデータ

クラス全体の前提や多くのテストで共通する対象は、具体型のreadonlyフィールドとコンストラクターで準備する。一つのテストだけの値は原則ローカルに置き、準備の抽出は共通AGENTSの「テストの設計と準備」に従う。共通化するためだけのフィールド・定数は増やさない。

見て意味が分かる短い期待値はアサーション内に置く。長いGUIDや時刻など、値だけでは何のデータか読めないサンプルには意味のある名前を付ける。期待値を分離するのは複数回利用、長さによる読みにくさ、独立概念、別々にデバッグする価値があるときとする。

### Fluentなアサーション

採用ライブラリとバージョンで使えるAPIを確認する。`Should()` と最終アサーションは原則同じ行に置き、英文の述語を分断しない。短いプロパティ、`Which`、`ToString()` も一続きの句として読めれば縦に切りすぎない。長い期待値は引数側で改行する。

例外の複数プロパティを検証するときは例外アサーションを一度だけ実行して変数へ受け、`Which` から各検証へつなぐ。`Which` の結果を受けるだけの別変数を増やさない。

```csharp
var action = () => tested.Execute();
var thrown = action.Should().Throw<ArgumentException>();
thrown.Which.ParamName.Should().Be("value");
thrown.Which.Message.Should().Contain("value");
```

nullableな値の非null性を仕様として確認する場合に `NotBeNull()` を使う。採用版のnullable解析に対応した検証後は、同じ値を続けて使うためだけの `!`、`?? throw`、`Which` を足さない。コンパイラが保証した事実まで別Assertで重ねない。

整理するときは検証内容、テスト名、Skip状態と理由、列挙回数、評価タイミングを保つ。英語名や変数の数ではなく、どの振る舞いを確認するかが読めることを判断基準にする。
