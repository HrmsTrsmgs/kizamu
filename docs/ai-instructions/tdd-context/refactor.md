# Refactor: 外部契約を保って内部設計を整える

共通 `tdd-workflow/references/refactor.md`（`codex-workflows e66db1d`）のリポジトリ内参照版。

`common.md` とこの文書だけを工程指示として読む。GのSHA、対象設計領域、現行コード・テスト・契約、品質規約、必要な呼び出し元と先を読む。Greenの思考過程や未実装要求一覧は引き継がない。

差分は読み直す場所の索引であり、現行コードの代用品ではない。継続する場合は最後に同期したSHAからGまでを確認し、版や契約が不明なら現行の正本から組み立て直す。

抽象化を主要な検討事項とし、今回の追加行だけでなく対象領域の意味・変更理由・責務・依存・命名・変更波及を見る。似た形だけで共通化せず、現在の責務を局所化する。未確定の将来機能や形式的な拡張点は増やさない。

Greenから分けたアルゴリズムの正当性とロジックの不足もここで検討する。検討自体を省略せず、既存契約に対する不足が見つかった場合は以下の手順で別のRedへ渡し、挙動変更をRefactorへ混ぜない。

現在の外部挙動を保つ一般化は、テストが内部構造を指定していないことだけを理由に禁止しない。小さな変更ごとに検証し、テスト成功を任意の変更の同値証明にしない。

三角測量途中の固定値、特定入力への直書き、処理対象の限定などにより、既存要求・外部契約を満たせていないことが明らかで確認テストがない場合は、最小利用例を理由・解除条件付きのSkipテストにする。現在の仮挙動や内部構造を期待値にせず、不足機能の実装・挙動を変える一般化は別のRedとGreenへ渡す。

一般則が複数考えられて外部挙動を確定できない場合は、区別できる利用例と必要な判断を返す。未テストの既存分岐を発見しただけで新仕様を決めない。未決定の追加機能は対象と理由を報告し、候補を増やす調査・設計をしない。

抽出した内部APIや移動した責務には、その責務に必要なテストを同じRefactorで加える。これは既存の外部挙動を守るテストであり、新しい外部契約のRedとは区別する。外側の境界・結合テストを残す。テストの整理で意味を弱めず、テスト対象のためだけに公開範囲を広げない。

改善対象を検討し、なければコードを変えず、空コミットも作らない。変更があれば検証後も未コミット差分を残し、人間レビューを待つ。返すのは構造変更と理由、検証結果、Skipの場所・識別子・根拠・理由・解除条件、未確定事項。Greenを兼任しない。
