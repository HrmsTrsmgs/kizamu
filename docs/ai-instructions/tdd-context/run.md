# 進行役の手順

共通TDDの参照版。正本は `codex-workflows/skills/tdd-workflow/references/run.md`。

進行役は担当の起動、成果物の一方向の受け渡し、人間レビューの依頼、継続記録を担う。外部APIや内部設計を再審査する工程は追加しない。

## 開始とコンテキスト

要求、作業場所、ブランチ・HEAD・ステージ済み差分・未コミット差分、現在の工程、既定の検証方法を確認する。プロジェクトが指定した再開記録は進行役が読み、工程担当には必要な確定情報だけを渡す。未承認差分が前回のGreenなら、その人間レビュー境界から再開する。

挙動を維持するリファクタリングだけの依頼はRefactorから開始する。Gコミットがない場合は開始時のHEADを基準版とし、既存の未コミット差分と今回の対象を区別して渡す。形式だけのRed・GreenやGコミットを作らず、変更後の人間レビュー・コミット了承は維持する。

実在する委任ツールの仕様を確認し、親の会話履歴を渡さない指定で担当を起動する。履歴を継承するforkや同一チャット内の役割変更で代用しない。分離手段が使えなければその制約を報告し、この方式で続行したとは扱わない。新しいユーザー所有のチャット作成は、通常の内部委任とは別の操作として扱う。

同じ作業ツリーを順番に使用する。分離目的だけでworktreeを作り直さず、起動後に担当の作業場所を確認する。工程担当を並列編集させない。子への再委任や担当同士の相談を行わせない。

Redは同じ外部契約の設計中なら同じRed担当を継続できる。GreenはRedサイクルごとに新規担当とし、同じRedに対する失敗修正だけ継続する。Refactorは同じ設計領域で、最後に同期した版を特定できる場合に継続できる。工程をまたいで同一担当を使い回さない。版や契約が曖昧になった場合は現行成果物から新規に組み立てる。

## 通常の流れ

Red → Green → ユーザーが未コミット差分を確認 → 了承後にGコミット → Refactor → 実変更があればユーザーが未コミット差分を確認 → 了承後にFコミット → 次のRed。

ユーザーが「Redまで」「Greenまで」等と指定したらそこで停止し、コミットや次工程への許可と読み替えない。Refactorは検討を行い、改善対象がなければ変更もFコミットも作らない。空コミットを作らない。次の依頼がなければ終了する。

レビュー時は対象ファイル・変更内容・検証結果・メッセージ案を示し、了承前にステージやコミットをしない。ユーザーのIDE等で見られる差分を残す。担当の検証後に追加のAI意味レビューや、同条件の検証の再実行を挟まない。具体的な実行失敗や環境問題の確認、人間の修正指示への対応は必要な範囲で行う。

push・merge・releaseは個別の指示に従う。作業を任されたことだけで許可されたとは扱わない。

## 渡す情報

担当へはこのディレクトリ内の `common.md` と担当工程文書の実際のパスを渡し、プロジェクトの参照先を指定する。

| 担当 | 渡す内容 |
| --- | --- |
| Red (`red.md`) | 元の要求、利用場面、確定済みの契約、既知の互換性制約、既存API・テストを探索する参照先。未決定APIや完成実装を進行役が先に決めない |
| Green (`green.md`) | 今回のテストの場所・識別子、確認した失敗、確定契約、現行コード・関連テスト、ビルド・テスト方法、必須制約 |
| Refactor (`refactor.md`) | GのSHA（単独Refactorは開始時の基準SHAと差分）、対象設計領域、現行コード・テスト・契約、設計・品質規約。継続担当には最後の同期SHA |

Greenへ将来の候補、未採用案、Redの比較過程、Refactor方針を渡さない。RefactorへGreenの思考過程・弁明や未実装要求一覧を渡さない。長い思考要約や遵守宣言を工程間で引き継がない。

Redのテストが最初から正しく通るなら不要な実装を作らない。テストだけのコミットも人間レビューと了承に従う。未決定の外部契約が不可欠と報告された場合は、その判断だけをユーザーへ示す。進行役が新仕様を作って同じGreenへ差し戻さず、契約変更を新しいRedとGreenの対象とする。

## 不足と検討事項の記録

Refactorが追加したSkipは、場所・識別子・不足の根拠・理由・解除条件をユーザーへ示す。解除するグループはユーザーに確認し、グループ内では番号が最小のSkipを一つ解除する。同じ内容を文書へ重複記録しない。

テスト化されていない検討事項は既存テスト・記録との重複を確認し、プロジェクトが指定する候補・ロードマップ・再開記録の該当箇所へ残す。特定のファイル名が存在すると推測しない。既存の適切な置き場がなければ最小の記録先を設けて知らせる。対象、理由、確認済み事実、提案、未確認を分け、合意前に実装予定へ昇格させない。

候補一覧をGreen・Refactorへ渡したり、現在の工程へ追加実装として戻したりしない。人間レビュー待ちや中断時は、プロジェクトの既存記録へ現在位置と次の着手点を残す。
