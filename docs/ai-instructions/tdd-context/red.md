# Red: 利用側から外部契約を決める

共通TDDの参照版。正本は `codex-workflows/skills/tdd-workflow/references/red.md`。

`common.md` とこの文書だけを工程指示として読む。今回の要求と確定済み契約から、責務、呼び出し、入力、戻り値、外から見える状態変化を利用側から設計する。内部アルゴリズムや実装しやすさからAPIを逆算しない。

対象機能、同じドメイン、公開境界、類似ユースケース、呼び出し側、互換性に関係するテストやAPI利用例を検索する。最初から全テスト全文を読み込まず、既存テストの現行契約・互換性・旧仕様・意味未確認を根拠付きで区別する。

実装本体や内部設計資料は原則参照せず、AGENTSの既存コード確認はAPI宣言と利用例を中心に満たす。確定契約を毎回再設計せず、次の未充足の振る舞いを一件選ぶ。全件テスト計画や完成実装の計画を先に作らない。

テストに実際の利用者のcall siteを書く。呼び出しだけで意味が伝わるか、名前がドメインの言葉か、引数の意味・順序を推測させないか、実装都合の余分な手順がないか、既存APIと不必要に異ならないかを読む。具体的問題がある場合だけ代替案を比較する。

期待値は要求と外部契約から決め、現行実装の出力を写さない。一つの仕様を明らかにする複数Assertはよいが、独立した仕様を詰め込まない。公開API案をコンパイル可能にして示す場合だけ、`NotImplementedException` 等の最小スタブを追加できる。

仕様変更は既存テストを新契約に合わせて変更し、意図したRedを確認する。他の期待値を実装都合で弱めず、privateの直接検査のためだけに公開範囲を広げない。明示的に投げる例外契約は原則先にテストで示す。

テストを実行し、API未存在、スタブ、検証したい振る舞い、環境障害による失敗を区別する。意図と違えばテスト・データ・契約へ戻り、Greenへ進まない。最初から正しく通る場合は成功を受け入れ、実装を壊してRedにしない。

合意済みの将来観点をまとめて記録する場合は重複を確認し、理由と解除条件付きのSkipとして残す。Skip理由の先頭にグループ名とグループ内番号を付ける。データごとに段階的に扱う場合は各データを個別にSkipする。採用中のテスト基盤で対応できない場合は実現方法を確認し、無断で依存関係を変更しない。未合意の将来仕様を増やさず、解除するグループはユーザーに確認する。指定されたグループでは番号が最小のSkipを一つだけ解除する。対象が一意に決まらなければ変更せず報告する。解除用スクリプトを利用できる場合はAIが実行してよい。解除対象と差分を確認し、テストを実行して意図したRedを確認する。

返すのは今回のテストの場所・識別子、実行結果、意図した失敗の根拠、確定契約、新APIの意図。比較過程や残りの候補をGreenへ渡さず、実装に進まず終了する。
