# TDD作業指示

この文書は、振る舞い追加、仕様変更、不具合修正に適用する。
C#以外の開発にも共有できる内容として扱う。

## 基本

* 振る舞いの追加や変更、不具合修正では、原則として実装前に外部から観測できる振る舞いのテストを追加する。
* 不具合修正では、可能な限り再現テストを先に追加する。
* Red、Green、Refactorを区別し、「Redまで」「Greenまで」「Refactorまで」と指定された場合はその段階で停止する。
* Red確認では、失敗したコマンド、失敗理由、意図した失敗かどうかの判断根拠をユーザーへ報告する。
* Red確認が意図した失敗でない場合は、Green実装へ進まず、テスト、仕様、テストデータ、既存設計の確認へ戻る。
* 公開APIを追加または変更する場合は、Red段階のテストをAPI案として扱う。
* APIレビューのためにコンパイルを通す必要がある場合は、`NotImplementedException` などで失敗する最小限の公開APIスタブを追加してよい。
* プロジェクト生成や単純な設定・文書変更に、意味のないRedテストを形式的に作らない。

## Skip保留仕様

* API仕様をまとめて検討するためにGreen対象より多いテストを先に書く場合は、保留する仕様テストに理由付きの `Skip` を付ける。
* `Skip` 理由は、後から読んだ人が、なぜ今は実行対象でないのか、いつ解除するのかを判断できる内容にする。
* `Skip` 理由に単に「未実装」とだけ書かない。
* `Skip` 属性の行から理由が読み取りにくくなる場合は、共通定数化せず文字列を直接書く。
* `Skip` 済み仕様テストは、Green対象にするまで原則として変更しない。
* `Skip` で保留した仕様をGreen対象へ移す場合は、どのテストの `Skip` を外すかをユーザーに確認してから進める。

## Green対象と過剰実装

* Green対象は、一つのテスト、またはユーザーと明示的に合意した小さな仕様のまとまりに限定する。
* Greenでは、現在有効な対象テストを通すための必要最小限の実装を行う。
* 必要最小限とは、対象テストが要求する振る舞いを実現することであり、Green対象外の仕様を先取りして固定することではない。
* AIが先の仕様や必要になりそうな実装を推測した場合も、Green対象外なら実装せず、推測として報告する。
* Green中に対象テストとは別の仕様が必要だと分かった場合は、実装せず、理由付きの `Skip` テストまたは確認事項として残す。
* 対象テストが要求していない実装を先に入れ、その後でRedテストを追加して正当化しない。
* 共通処理への実装で、まだ `Skip` している次の仕様テストまで通りそうな場合は、実装前に影響範囲を報告する。
* Green対象外の `Skip` 済み仕様テストやテストデータ全体の整理が必要に見えた場合は、編集前に理由を報告して止まる。
* Green対象を理解するために必要なテストデータ、期待値、補助APIだけを同じ作業単位に含める。
* 予定テストを失敗させ続けるために、公開APIを不自然または不完全な形へ歪めない。
* 同じAPIの正常系と異常系が同じ自然な実装で満たされる場合は、予定テストが通ること自体を避けるための迂回実装をしない。
* Greenの実装へ着手する前に、対象Redを通すために必要な入力、実行経路、期待結果を限定する。対象Redに現れない場合を先回りして、条件分岐、フォールバック、状態遷移、例外型、エラーメッセージ、戻り値仕様を設計または記述しない。
* テストに直接記述されていない処理を、機械的に過剰実装と判断して削除しない。対象仕様を実現する自然な処理、標準APIの利用に伴う処理、独立した仕様を追加する処理を区別する。
* 新しい条件分岐や状態遷移を独立した仕様として追加する場合は、実装が簡単であっても、その意図と期待結果を示すテストを先に追加する。後日の変更対象になり得ることを、未検証のまま残してよい理由にはしない。
* Green後に未テストの独立した分岐や状態遷移が見つかった場合は、Green着手前の限定が不十分だったものとして、Green対象外の実装を削除する。必要な振る舞いだと判断した場合も、実装を残したまま後付けで正当化せず、実装を戻してRedから追加する。
* 自分で `throw` を書く例外は仕様として扱い、原則として先にテストで固定する。
* 低水準API、標準ライブラリなどの呼び出し結果として自然に発生する例外まで、すべて明示仕様にする必要はない。

## Refactorとテスト保守

* Green確認後に、外部から観測できる振る舞いを変えずにリファクタリングする。
* 責務を新しいクラスやレイヤーへ移した場合は、その責務が独立して判断する振る舞いを、対応するテストレイヤーで同じリファクタリング単位に確認する。
* 責務分離後も、HTTPや画面など外側の境界と依存関係の結合を確認する既存テストは残す。下位レイヤーの単体テストを追加したことだけを理由に、外側のテストを削除しない。
* 既存テストを、実装に都合よく弱めたり削除したりしない。
* テストが誤っている可能性がある場合は、勝手に変更せず報告する。
* 実装済みの仮挙動を仕様として固定するテストを、理由なく追加しない。
* テスト数を増やすこと自体を目的にしない。
* 一つのテストに一つのAssertだけを機械的に強制しない。
* 複数の期待結果が独立して壊れ得て、それぞれ自然な仕様名を付けられる場合は、Assert数ではなく仕様の違いを理由にテストを分ける。
* 内部変数やprivateメソッドを直接テストするためだけに設計を歪めない。
* 実装予定のテストが通らない状態を維持することは仕様ではない。
* 将来のテストを通さないために、現在の実装を不自然に読みにくくしない。
* テストを実行順序、開発者固有のパス、現在時刻、タイムゾーン、実時間待機へ不必要に依存させない。
* 将来タイマーを実装する際は制御可能な時刻供給元を使い、経過時間をテスト可能にする。
