# TDD作業指示

この文書は、振る舞い追加、仕様変更、不具合修正に適用する。

## Red

* 原則として実装前に、外部から観測できる振る舞いを表すテストを追加する。
* 不具合修正では可能な限り再現テストを先に追加する。
* 失敗したコマンド、失敗理由、意図した失敗かどうかの根拠を報告する。
* 意図した失敗でなければGreenへ進まず、テスト、仕様、データ、既存設計の確認へ戻る。
* 公開APIのRedテストはAPI案として扱う。レビューにコンパイルが必要なら、失敗する最小限のスタブを追加してよい。
* プロジェクト生成や単純な設定・文書変更に、意味のないRedテストを形式的に作らない。

## Green

* Green対象を一つのテスト、または合意した小さな仕様のまとまりに限定する。
* 現在有効な対象テストを通す自然な最小実装を行い、将来仕様を先取りしない。
* 対象外の分岐、例外型、メッセージ、戻り値仕様を推測で追加しない。
* 自分で投げる例外は仕様として扱い、原則として先にテストで固定する。
* 対象外の仕様が必要と分かった場合は実装せず、確認事項として報告する。
* 先に実装してからRedテストを追加して正当化しない。

## 保留仕様

* Green対象より多い仕様テストを先に書く場合は、理由と解除条件が分かる `Skip` を付ける。
* `Skip` 理由を単に「未実装」としない。
* 保留したテストはGreen対象にするまで原則変更せず、解除前に対象をユーザーへ確認する。
* 保留テストを失敗させ続けるために、公開APIや実装を不自然に歪めない。

## Refactorとテスト保守

* Green確認後に、外部から観測できる振る舞いを変えずにリファクタリングする。
* 既存テストを実装に都合よく弱めたり削除したりしない。
* テストが誤っている可能性がある場合は、勝手に変更せず報告する。
* テスト数を増やすこと自体を目的にせず、一つのテストに一つのAssertだけを機械的に強制しない。
* privateメンバーを直接テストするためだけに設計を歪めない。
* テストを実行順序、開発者固有のパス、現在時刻、タイムゾーン、実時間待機へ不必要に依存させない。
* 将来タイマーを実装する際は制御可能な時刻供給元を使い、経過時間をテスト可能にする。
* 「Redまで」「Greenまで」「Refactorまで」と指定された場合は、その段階で停止する。
