# TDD作業指示

この文書は、振る舞い追加、仕様変更、不具合修正、リファクタリングに適用する。
C#以外の開発にも共有できる内容として扱う。
複数チャットで各段階のコンテキストを分離する場合は、`tdd-orchestration.md` も参照する。

## 基本

* TDDは、作業だけでなく考える対象をRed、Green、Refactorへ分け、実行結果からフィードバックを得る手順として扱う。各段階で行わない検討を、単に優先順位が低いだけと解釈して混ぜない。
* 振る舞いの追加や変更、不具合修正では、原則として実装前に外部から観測できる振る舞いのテストを追加する。
* 不具合修正では、可能な限り再現テストを先に追加する。
* Red、Green、Refactorを区別し、「Redまで」「Greenまで」「Refactorまで」と指定された場合はその段階で停止する。
* プロジェクト生成や単純な設定・文書変更に、意味のないRedテストを形式的に作らない。

## Redと外部設計

* Redでは、必要な振る舞い、APIの外部設計、使い勝手を考える。実装方法、実装しやすさ、テスト全体の網羅性の検討を同時に持ち込まない。思いついた別の観点は保留し、今の一件に集中する。
* 期待仕様が明確でテストを実行できる場合は、既存テスト・API・データを必要な範囲だけ確認してテストを書き、実行結果から失敗理由を確認する。Redになる見込みを予測・説明するためだけに実装を調査したり、推論へトークンを費やしたりしない。
* Red確認では、失敗したコマンド、失敗理由、意図した失敗かどうかの判断根拠をユーザーへ報告する。
* Red確認が意図した失敗でない場合は、Green実装へ進まず、テスト、仕様、テストデータ、既存設計の確認へ戻る。
* 公開APIを追加または変更する場合は、Red段階のテストをAPI案として扱う。
* APIレビューのためにコンパイルを通す必要がある場合は、`NotImplementedException` などで失敗する最小限の公開APIスタブを追加してよい。

## Skip保留仕様

* API仕様をまとめて検討するためにGreen対象より多いテストを先に書く場合は、保留する仕様テストに理由付きの `Skip` を付ける。
* ユーザーと後で確認することに合意したテスト観点は、既存テストとの重複を確認したうえで、口頭の予定だけにせず理由付きの `Skip` テストとして残す。既存実装で成功する見込みでも、未レビューなら同様に保留する。未合意の将来仕様を先回りして追加する根拠にはしない。
* `Skip` 理由は、後から読んだ人が、なぜ今は実行対象でないのか、いつ解除するのかを判断できる内容にする。
* `Skip` 理由に単に「未実装」とだけ書かない。
* `Skip` 属性の行から理由が読み取りにくくなる場合は、共通定数化せず文字列を直接書く。
* `Skip` 済み仕様テストは、Green対象にするまで原則として変更しない。
* `Skip` で保留した仕様をGreen対象へ移す場合は、どのテストの `Skip` を外すかをユーザーに確認してから進める。
* 例外として、Refactorで既存の確定仕様や外部契約から明らかな機能不足を発見し、その振る舞いを確認する既存テストがない場合は、ユーザーとの事前合意なしに不足を示す最小の利用例を理由と解除条件付きの `Skip` テストとして追加してよい。Skipを外してRed・Greenへ進む際は、どのテストを有効にするかユーザーへ確認する。

## Green対象と過剰実装

* Green対象は、一つのテスト、またはユーザーと明示的に合意した小さな仕様のまとまりに限定する。
* Greenでは、現在有効な対象テストを通すための必要最小限の実装を最初から書く。事後チェックで削ることを前提に実装を増やさない。
* Greenでは、内部設計を整えること、アルゴリズム全体の正当性の検討、ミスがないかの注意深い目視確認を行わない。対象テストを早く通すことに集中し、設計とロジックの検討はRefactorへ分ける。
* Greenの動作確認には自動テストを積極的に使う。成功するかを長く推論するより、対象テストを実行し、結果に基づいて修正する。関連テストや全体テストで既存動作への影響も確認し、実装を最小限にする判断と動作確認を混同しない。
* Green・Refactorの最終確認とコミット前には、原則として影響する実装の全テストを実行する。対象テストや関連テストだけで済ませるのは、変更が残りのテストへ影響しないことを依存関係や実行経路から説明できる場合に限り、その理由を報告する。所要時間だけを省略理由にしない。影響しないか長く推論するより、全テストを実行するほうが低コストなら実行する。
* 必要最小限とは、対象テストが要求する振る舞いを実現することであり、Green対象外の仕様を先取りして固定することではない。
* AIが先の仕様や必要になりそうな実装を推測した場合も、Green対象外なら実装せず、推測として報告する。
* Green中に対象テストとは別の仕様や未確認の振る舞いに気づいた場合は、実装を追加せず、対象、気づいた内容、必要と考えた理由を終了報告へ簡潔に添える。確認済みの事実と提案・未確認事項を区別し、過剰実装を正当化する材料にしない。候補を増やすための調査や設計は行わない。候補の重複確認と継続記録は統合チャットへ渡す。
* 対象テストが要求していない実装を先に入れ、その後でRedテストを追加して正当化しない。
* 共通処理への実装で、まだ `Skip` している次の仕様テストまで通りそうな場合は、実装前に影響範囲を報告する。
* Green対象外の `Skip` 済み仕様テストやテストデータ全体の整理が必要に見えた場合は、編集前に理由を報告して止まる。
* Green対象を理解するために必要なテストデータ、期待値、補助APIだけを同じ作業単位に含める。
* 予定テストを失敗させ続けるために、公開APIを不自然または不完全な形へ歪めない。
* 同じAPIの正常系と異常系が同じ自然な実装で満たされる場合は、予定テストが通ること自体を避けるための迂回実装をしない。
* Greenの実装へ着手する前に、対象Redを通すために必要な入力、実行経路、期待結果を限定する。対象Redに現れない場合を先回りして、条件分岐、フォールバック、状態遷移、例外型、エラーメッセージ、戻り値仕様を設計または記述しない。
* テストに直接記述されていない処理を、機械的に過剰実装と判断して削除しない。対象仕様を実現する自然な処理、標準APIの利用に伴う処理、独立した仕様を追加する処理を区別する。
* Green確認後の過剰実装点検は、今回追加したロジックと対象テストとの対応に限定する。対象仕様に不要な分岐、代入、初期化、後始末などがあり、取り除いても対象テストと既存テストが通る場合は、削除してからGreen完了とする。既存コードやアルゴリズム全体の点検へ広げない。
* 新しい条件分岐や状態遷移を独立した仕様として追加する場合は、実装が簡単であっても、その意図と期待結果を示すテストを先に追加する。後日の変更対象になり得ることを、未検証のまま残してよい理由にはしない。
* Green後に未テストの独立した分岐や状態遷移が見つかった場合は、Green着手前の限定が不十分だったものとして、Green対象外の実装を削除する。必要な振る舞いだと判断した場合も、実装を残したまま後付けで正当化せず、実装を戻してRedから追加する。
* 自分で `throw` を書く例外は仕様として扱い、原則として先にテストで固定する。
* 低水準API、標準ライブラリなどの呼び出し結果として自然に発生する例外まで、すべて明示仕様にする必要はない。

## Refactorとテスト保守

* Green確認後に、外部から観測できる振る舞いを変えずにリファクタリングする。
* 動作確認できるコードを読みやすく整理しながら、内部設計やロジックの妥当性を検討する。小さな変更ごとにテストを実行し、ミスがないという目視の確信で代替しない。
* 検討の結果、整理が不要ならコード変更は行わない。ただし、テスト成功を理由に検討自体を省略しない。「Greenまで」の指定で停止した場合は、Refactorでの検討は未実施として引き継ぎ、完了扱いにしない。
* Refactorでは抽象化を最も重要な検討事項とする。現在の責務、重複、変更理由から一般則が明確なら、外部挙動を保ったまま一般化してよい。一般則を判断できない場合は、区別できる具体例をRed候補としてユーザーへ提示する。テストが内部構造や抽象化を直接要求していないことだけを理由に、一般化を禁止しない。
* クラスやメソッドを抽出・新設する場合も、既存の振る舞いを移すことに限定する。新しいクラスの一般的な役割を理由に、対応する入力、例外処理、保存方法などの新機能を追加しない。既存テストがすべて通ることだけで、新機能の混入がないとは判断しない。
* Refactorでは、三角測量途中の定数返し、特定入力への直書き、処理対象を限定した分岐など、明らかに要求を満たせていない実装も確認する。既存の要求や外部契約から不足する振る舞いが明確で、それを確認するテストがない場合は、対象責務のテストへ理由と解除条件を明記した `Skip` テストを追加してよい。不足を示す最小の利用例で外部から観測できる振る舞いを確認し、実装構造や現在の仮挙動を期待値にしない。実装の一般化や機能追加は行わず、Skipの解除とRed・Greenは別工程へ渡す。追加したSkipの場所、識別子、不足の根拠、Skip理由、解除条件をユーザーに報告し、開発候補の文書へ重複記録しない。
* 期待する振る舞いが未決定の追加機能や誤りに気づいた場合は、対象、気づいた内容、必要と考えた理由を終了報告へ簡潔に添える。確認済みの事実と提案・未確認事項を区別する。候補を増やすための調査や設計は行わず、重複確認と継続記録は統合チャットへ渡す。未テストの既存分岐を見つけたことだけで、新しい仕様やRed予定を決めない。
* 責務を新しいクラスやレイヤーへ移した場合は、その責務が独立して判断する振る舞いを、対応するテストレイヤーで同じリファクタリング単位に確認する。
* 責務分離後も、HTTPや画面など外側の境界と依存関係の結合を確認する既存テストは残す。下位レイヤーの単体テストを追加したことだけを理由に、外側のテストを削除しない。
* 既存テストを、実装に都合よく弱めたり削除したりしない。
* テストが誤っている可能性がある場合は、勝手に変更せず報告する。
* 実装済みの仮挙動を仕様として固定するテストを、理由なく追加しない。
* テスト数を増やすこと自体を目的にしない。
* 一つのテストに一つのAssertだけを機械的に強制しない。
* 複数の期待結果が独立して壊れ得て、それぞれ自然な仕様名を付けられる場合は、Assert数ではなく仕様の違いを理由にテストを分ける。
* 内部変数やprivateメソッドを直接テストするためだけに設計を歪めない。
* 実装予定のテストが通らない状態を維持することは仕様ではない。
* 将来のテストを通さないために、現在の実装を不自然に読みにくくしない。
* テストを実行順序、開発者固有のパス、現在時刻、タイムゾーン、実時間待機へ不必要に依存させない。
* 将来タイマーを実装する際は制御可能な時刻供給元を使い、経過時間をテスト可能にする。

## 仕様変更の手順

1. 変更したい振る舞いのテストを新仕様に合わせて修正し、意図したRedを確認する。
2. そのテストを通す必要最小限の実装変更を行う。
3. ほかのテストが失敗した場合は、新仕様によって変更すべき期待か、維持すべき振る舞いの回帰かを精査する。前者は期待を修正してRed→Greenを進め、後者は期待を維持して実装を直す。実装結果に合わせて期待値を追従させない。
4. 変更後も有効な既存テストを含めてすべてGreenにしてから、リファクタリングする。

## 別実装への移植

* 移植元の既存テストを起点に、利用者視点の振る舞いを確認する。移植先に自然な対応がある場合だけ、その実装向けのRedへ読み替える。
* 移植元に固有で対応する概念がない機能を、機械的に移植しない。対応させるためだけの不自然な抽象化や代替APIを作らない。
* 元テストのコードを単純置換せず、何を観測するテストかを保った最小のテストとして書く。対応元、読み替え、対象外とした理由を報告する。
* 一度に扱う仕様は、ユーザーと合意した単位を超えない。Skipテストを含む全テストはコンパイルできる状態を保ち、未着手のAPIは必要な最小スタブに限定する。
