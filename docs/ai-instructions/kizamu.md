# Kizamu固有作業指示

## プロジェクトの目的

Kizamuを第三者がビルド、テスト、利用、レビューできるアプリケーションとして整備する。
機能数より、記録操作の軽さ、理解しやすいUI、責務分離、変更箇所の局所化、テスト可能性を優先する。
詳細な製品コンセプトは `docs/concept.md` を参照する。

## 製品設計

* 時間の記録操作と、分類、編集、管理、集計を別の関心事として扱う。
* 記録開始時にプロジェクト、作業分類、集計用属性などの入力を強制しない。
* 未分類でも記録でき、必要になった時点で後から整理できる設計を優先する。
* プロジェクト管理を毎回の時間記録の前提にしない。
* 記録画面を集計表や管理画面の一部として設計しない。
* プロジェクト配下の作業は、深さごとの意味を固定しない汎用的な作業ノードのツリーとして扱う。
* 標準UIは浅い階層を扱いやすくしてよいが、データ構造の深さを不必要に制限しない。
* 時間記録は末端に限らず、任意の作業ノードへ紐付けられる構想を維持する。
* UIによって利用者の分類思想や管理方法を過度に規定しない。
* 管理できる仕組みは用意しても、管理そのものへ多くの手間を要求しない。

## 実装範囲と外部連携

* 必要になっていない画面、レイヤー、型、インターフェース、永続化を先行実装しない。
* 時間配分は補助機能であり、Kizamuの主機能として扱わない。
* ClockifyをKizamuの前提にせず、Clockifyのデータ構造を内部モデルとして採用しない。
* Clockify連携は、独立したKizamuが外部サービスとの相互運用性を持つものとして設計する。
* ローカル保存、サーバー永続化、ログイン、ユーザー管理は、仕様が確定するまで追加しない。

## 開発環境と文書

* ASP.NET CoreとReactは責務を分離しつつ、標準的なVisual Studio、Vite、SPA proxyの統合を優先する。
* 独自の複雑な起動基盤や将来用の共通ライブラリを作らない。
* READMEの起動、ビルド、テスト、Lint手順は、実際に確認した構成と一致させる。
* 利用者向け文書と画面表示は日本語にし、コード上の識別子は各言語の標準的な英語命名規則に従う。
* 未実装機能をREADMEや画面で利用可能なように見せない。
* 次の実装対象を時間記録と決め打ちせず、小さな単位で仕様を確定してから進める。
