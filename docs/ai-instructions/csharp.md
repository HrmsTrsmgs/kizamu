# C#/.NET開発指示

## プロジェクトの補足

共通Skill `csharp-conventions` を使う場合は、この節だけを追加で確認する。未導入時は後述の参照版も使う。

* プロダクトコードの識別子は、ポートフォリオとして第三者が読みやすい標準的な英語にする。
* .NETテストはxUnit.net v3を使う。採用パッケージは `xunit.v3.mtp-off` 4.0.2と `xunit.runner.visualstudio` 4.0.1。VSTestによる既存の `dotnet test` とVisual Studio Test Explorerの経路を維持し、Microsoft Testing Platformへの移行は含めない。
* 取消可能な非同期APIには `Xunit.TestContext.Current.CancellationToken` を渡す。テスト本体では [TestCancellation](../../tests/TestSupport/TestCancellation.cs) の読み取り専用プロパティを `using static` で読み込み、`CancellationToken` と記述する。このstatic usingは、暗黙に読み込まれる型名との衝突を避けるため名前空間内（file-scoped namespace宣言の後）に置く。共通ソースは利用するテストプロジェクトへソースリンクし、クラスごとのgetterを重複させない。アクセス時のテストコンテキストを参照し、コンストラクターやstaticフィールドへキャッシュしない。テストのためだけに製品APIへ引数を追加せず、既存の対応APIに適用する。
* 複数列の `TheoryData` は、型と検証する組合せを維持できる場合、v3のタプルを使ったコレクション式で記述する。単一列など既に簡潔な記述を、記法統一のためだけに冗長にしない。
* ASP.NET Core統合テストでは、必要に応じて `WebApplicationFactory` を使い、HTTPパイプラインを通す。
* .NETテストでは、Apache-2.0のOSSフォークであるAwesomeAssertionsを使う。既存のFluentAssertionsからの移行は、機能追加やAI指示の取り込みとは別の変更単位にする。
* テスト準備・Moq等の固有方針は [テスト記述の補足](../testing-style.md) の該当節を使う。C#の共通記法を参照版と重ねて読まない。
* 検証対象は変更した実装の実在するソリューション・プロジェクトとする。非増分ビルド・SARIF・formatの条件は共通Skillの `references/verification.md`（未導入時は後述の「コード変更の検証」）に従う。

## 未導入環境の参照版

Kizamu、両AsData、Kotowariで育てた規約を統合したもの。既存の `.editorconfig`、言語バージョン、公開契約、一貫した命名を確認し、全体の書式変更は依頼された単位に限定する。

テストを書く・整理する場合は [テストの記述](../testing-style.md#csharp共通記法)、規約の理由を説明する場合は [選択理由](#規約の選択理由)、コード変更の検証時は [ビルドと診断](#コード変更の検証) を読む。工程別TDDでは担当工程の範囲を越えて設計しない。

## 記述と命名

- 型推論や言語仕様で明白な情報を重ねず、明示は意図や境界の理解に役立つ場合に残す。
- 既定が `private` のメンバーには `private` を書かない。既定と異なるアクセス範囲は明示する。
- privateフィールドの既定方針は接頭辞なしのcamelCase。引数等と衝突する箇所はフィールド側に `this.` を付ける。既存の一貫した別規約を機械的に置換しない。
- 生成型が代入先・戻り型・引数型から明白なら、可読性やオーバーロード解決を損なわない範囲でtarget-typed `new` を使う。
- 固有の意味がないラムダ引数は `it`、未使用引数とdiscardは `_`、拡張レシーバーは `self` とする。
- 対象バージョンで利用可能なら `extension(T self)` を使う。構文の一括移行は別の変更単位にする。
- 値を返すだけの短いメソッド・プロパティ・インデクサーは、読みやすければ式形式を使う。
- 配列・コレクションの生成や必要な具体化は、対象バージョンで使え、型と評価順序を保てるならコレクション式を優先する。既存列から配列を作る場合も `[.. source]` を候補にし、記法のためだけに具体化しない。
- 三項演算子は条件と両結果が一息に読めるときだけ一行にする。それ以外は条件・真側・偽側を分けて `?` と `:` を行頭へ置く。偽側へ連鎖するときは `else if` の列としてフラットに読み、`: 次の条件` と最終の `: 結果` は最初の条件と同じ深さ、`? 結果` は一段深くする。
- 入れ子の生成式を複数行にする場合は `=` の後で分け、コンストラクターと依存オブジェクトの境界を改行・インデントで表す。次の呼び出しへ渡すだけの中間変数へ分解しない。
- 一時変数は評価回数、概念境界、共有、デバッグに意味がある場合に作る。添字・位置・分割結果に意味のある名前を付ける場合も含め、次の呼び出しへ渡すだけの変数は増やさない。英語名を付けること自体を可読性向上とみなさず、日本語の仕様語彙を曖昧にしない。
- 標準ライブラリと言語機能は、短さだけでなく表す意味に合わせて選ぶ。
- 公開APIは通常の.NET命名に合わせる。テストは日本語の仕様語彙を使える。製品コードの言語などプロジェクト固有の方針は、そのプロジェクトに従う。

## LINQ、型、null

- 絞り込み・対応付け・変換・集約は極力LINQへ寄せ、メソッド構文が明確に読みやすい場合以外はクエリ構文を使う。性能や互換性に関するプロジェクトの判断は維持する。
- `let`、`select`、タプル、匿名型で値を準備し、`foreach` には代入・書き込みなど副作用を伴う実行を置く。副作用を `Select` に押し込めず、`Array.ForEach` と `List<T>.ForEach` は使わない。
- 評価回数、順序、遅延実行を保つ。ループのためだけの `ToArray`・`ToList` や一時変数を作らない。列挙元を変更する等、具体化が必要なら理由を明確にする。
- `foreach` やクエリの `in` の右辺が複数行なら、`in` の直後で改行して右辺の範囲をインデントで示す。
- 存在・全件判定は `Any`・`All`。`Single` はちょうど1件、`SingleOrDefault` は0件を通常として複数を前提違反、`First` 系は一意性を要求しないときに選ぶ。例外を出す手段として選ばず、標準APIの例外を公開契約にするかはテストで固定する時点で判断する。
- `dynamic` への境界は一時変数で示し、対象・アクセス用途が分かる名前にする。既知の型へ戻すときは代入先の型を明記する。式中のキャストが読みにくければ `as` や明示型代入を検討し、値型など `as` が使えない場合は必要最小限のキャストにする。
- nullable警告を消すために `!` で事実を作らない。使うなら不変条件と理由が読み手にも追えることを確認する。

## XMLコメント

- publicメンバーはAPI利用者へ、外から見た役割・引数・戻り値・例外・制約を説明する。
- internal/privateメンバーはコードを読む人へ、実装意図・状態・不変条件・キャッシュ・遅延生成などの判断材料を書く。
- 名前や型の言い換えだけにせず、実装以上に細かく陳腐化しやすい説明を避ける。振る舞いや制約を変更したらコメントも更新する。

## テストの構成

- 既存フレームワークを使い、テストは実際の公開型・責務に対応する既存クラスへ追加する。長さや将来の増加だけで先回りしてクラスを分けない。
- 新しいテスト名は原則として日本語文で振る舞いと期待結果を表す。HTTP APIや画面等は利用者に読める敬語にし、内部処理には敬語を機械的に強制しない。既存の別規約や言語を変更する場合は範囲を確認する。
- 静的型で保証される型を実行時Assertしない。型自体を示すAPI例が必要なら明示型で受ける。
- 委譲する処理は代表経路で接続と同等性を確かめ、委譲先の全仕様を二重にテストしない。委譲元独自の対応付け等は個別に確認し、既存テストを一括削除する根拠にはしない。
- 実行順序、共有出力、個人のパス、カルチャー、時刻へ不必要に依存しない。一時ファイルはテストごとに分け、可能なら終了時に削除する。無関係な網羅のためだけにケースを増やさない。
- AwesomeAssertionsかFluentAssertionsかはプロジェクトの採用状態に従う。このSkillの適用だけで移行・追加しない。

## コード変更の検証

対象ソリューション・プロジェクト、`global.json`、SDK、フレームワーク、復元状態と既存コマンドを確認する。他プロジェクトのソリューション名やパスを使い回さない。

コード変更後は対象・関連テストから確認し、Green・Refactorの最終確認とコミット前には原則として影響する実装の全テストとビルドを実行する。残りに影響しないと依存関係や実行経路から説明できる場合だけ範囲を絞り、理由を報告する。所要時間だけを除外理由にせず、説明のための長い推論より実行が安価なら実行する。

同じコード・設定・実行条件で済んだ検証を、担当の受け渡しや診断確認のためだけに再実行しない。文書だけの変更には無関係なコード検査を要求しない。

### スタイルと解析

新規・変更箇所は `.editorconfig` の提案レベルの指摘も確認する。振る舞い、互換性、性能、可読性のために適用しない場合は理由を報告する。

工程完了時やコミット前のコード検証では、実在する対象を指定して、原則として次のオプションによる非増分ビルドと静的検査を行い、所要時間を確認する。下の `<対象>` は実際のパスへ置き換える説明用の表記である。

```text
dotnet build <対象> --no-restore --no-incremental -p:UseSharedCompilation=false -p:EnforceCodeStyleInBuild=true -p:RunAnalyzersDuringBuild=true -p:ErrorLog=obj/ide-diagnostics.sarif
dotnet format <対象> --no-restore --verify-no-changes --severity info
```

復元前なら必要な復元を先に行い、外部通信の目的を明示する。プロジェクトの対象フレームワークやビルド設定で対応できない項目は理由を報告する。

終了コードや警告数だけで判断せず、生成されたSARIFの提案も読む。診断ファイルはコミットしない。Visual Studioとの解析器・拡張・対象・未保存状態の一致を確認せず、VSと完全に同じ検証だと断定しない。

診断は今回の変更箇所と既存箇所に分け、変更箇所は対処するか残す理由を示す。ユーザーがVSの指摘を報告したら直近の変更だけと決めつけず、診断コード・ファイル・行・内容と照合する。修正対象外とした指摘と、再現できなかった指摘を混同しない。

静的解析の修正でもテストの意図を保つ。static化などで検証対象が変わる場合は機械的に変更せず、必要な範囲だけ理由付きの抑制を検討する。指摘を消すためだけの無意味な処理は追加しない。

## 規約の選択理由

Kizamuで明文化した選択を、個人の既定方針として引き継ぐ。既存の別規約を一律に書き換える理由にはしない。

### 既定のprivateを省略する

明示する規約には宣言だけでアクセス範囲を把握できる利点がある。一方、既定がprivateの場所では同じ情報を重ねることになる。C#の既定規則に沿って差分となるアクセス範囲だけを記述し、情報密度を保つ方を選んだ。`.editorconfig` の `omit_if_default` 相当の選択であり、公開APIのアクセス範囲まで曖昧にする趣旨ではない。

### フィールドの接頭辞を付けない

`_camelCase` や `s_camelCase` には使用箇所だけでフィールドやstaticであることが分かり、名前の衝突を避けられる利点がある。一方、識別子全体に視覚的な記号を足すことになる。通常は名前・宣言・型の関係から読めることを優先し、衝突する箇所だけ `this.` で区別する方を選んだ。

これらはMicrosoftのコードスタイルで見られるアクセス修飾子の明示や `_` / `s_` 接頭辞とは異なる、個人の選択である。C#の必須構文や全コードベース共通の規則という意味の「標準」ではない。公開APIのPascalCase等は通常の.NET命名に従う。

比較対象はMicrosoft LearnのコードスタイルとIDE0040の `for_non_interface_members` 等であり、Visual Studioの既定動作、Framework Design Guidelines、Microsoftの各コードベースを単一の必須規約とは扱わない。staticであることが理解に必要なら、接頭辞だけでなく宣言や型名経由のアクセスで示す。

### 一時変数と抽象化

中間値へ英語名を付けただけでは、特に日本語の仕様を読むテストで情報が増えるとは限らない。概念・評価回数・共有・デバッグの境界が生まれるなら変数を作り、それ以外は式を直接読む方を選ぶ。インライン化そのものを目的化しない。

抽象化も同じで、現在の責務と変更理由を局所化することに価値がある。将来機能を予測して空の仕組みを増やすことと、現在の設計を整理することを区別する。
