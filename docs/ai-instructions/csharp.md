# C#/.NET開発指示

## コード

* .NETの標準的な命名規則、既存コード、既存アナライザーに従う。
* 言語仕様や型推論で明白な情報を重複して書かず、明示的な記述は設計意図や境界を読む助けになる場合に残す。
* コメントとXMLコメントは、コードの言い換えではなく、外部から見た役割、判断理由、境界、制約、不変条件を説明する。
* 警告を根拠なく抑制しない。
* null許容警告や型検査を通すためだけに `!` で事実を作らない。
* テストのためだけに型やメンバーの公開範囲を広げない。
* 単純な処理を不要なクラス、レイヤー、インターフェースへ分割しない。

## テスト

* 既存のテストフレームワークと命名規則を優先する。
* テスト名から対象の振る舞いと期待結果が読み取れるようにする。
* 一つのテストは、レビュー時に一つの仕様として読める粒度にする。
* 実装詳細ではなく、実際のHTTP応答など外部から観測できる振る舞いを優先する。
* ASP.NET Core統合テストでは、必要に応じて `WebApplicationFactory` を使い、HTTPパイプラインを通す。
* 実ファイルや一時ファイルを使う場合はテストごとに分離し、可能な限り終了後に削除する。
* 今回のユースケースに関係しないケースを、網羅性だけを目的に追加しない。

## ビルドとパッケージ

* 作業前に実在するソリューション、プロジェクト、対象フレームワーク、インストール済みSDKを確認する。
* `global.json` が存在する場合は指定を確認する。
* 実在する対象へ `dotnet restore`、`dotnet build`、`dotnet test` を実行する。
* C#の調査やリファクタリングでは、コンパイラ、テスト、`dotnet format`、アナライザー診断を利用して検索範囲を絞る。
* NuGetパッケージを必要性なく追加、更新、ダウングレードしない。
* ビルド警告が今回の変更によるものか既存のものかを区別する。
