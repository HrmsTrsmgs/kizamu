# TypeScript/React開発指示

## プロジェクトの補足

共通Skill `typescript-react-conventions` とこの節を使う。未導入時は後述の参照版も読む。

Nodeの業務APIはFastifyを使い、HTTP契約はVitestとFastifyの `inject` で検証する。対象パッケージは `kizamu-backend-node` と `kizamu-backend-node-tests`。ルートのlint・test・buildにはReactとNodeの両方を含める。Nodeへ画面配信やフロント側のAPI中継を持ち込まない。

* UIの標準表示言語と利用者向け文言は日本語とする。VitestとReact Testing Libraryを使う。
* アサーションは「対象 → should → 期待すること」の順に記述する。具体的な初期化・nullable・クラスの比較は [テスト記述](../testing-style.md#検証対象を直接アサーションへ渡す)、共通準備は同文書の「テストの準備と補助メソッド」に従う。DOM・モック専用の検証やクラス復元の厳密比較を記法統一のために弱めない。
* npm workspacesとlockfileをルートで管理する。通常は `npm ci`、変更後は対象テストと `npm run lint`、`npm test`、`npm run build` を実行する。
* Vite proxy、Visual Studioの起動統合、画面配信と業務APIの責務は [固有指示](kizamu.md#開発環境と文書) に従う。CLIの成功とIDEの実機確認を区別する。

## 未導入環境の参照版

Kizamuの技術別指示から、他のTypeScript・React開発にも適用できる部分を取り込む。表示言語、状態管理方式、採用パッケージ、起動統合は各プロジェクトの決定を確認する。

## コードとテスト

- strict設定、既存Lint、通常の英語命名に従う。`any`、型アサーション、非nullアサーションで不確かな状態を隠さない。
- コンポーネントに業務ロジックや通信詳細を集中させない。必要性のない汎用クライアント、状態管理、共通コンポーネント、カスタムフックは先行追加しない。
- API URLを画面へ直接埋め込まず、既存の通信境界や設定に従う。Vite proxy等を使う場合はプロジェクトの構成を確認する。
- `useEffect` の非同期処理は、アンマウント後の更新など副作用の寿命を確認する。
- 既存のテスト基盤を使い、利用者が観測する表示・操作を検証する。Vitest・React Testing Libraryの採用は既存決定に従い、共通規則の適用だけで依存を追加しない。
- 通信境界を差し替え、単体・コンポーネントテストから実外部通信をしない。外部サービスとの結合テストは別の明示された範囲として扱う。
- stateなど内部値を直接検査するために設計を歪めない。仕様を表す日本語のテスト名とデータ名を使い、既存の異なる命名は無関係に一括変更しない。
- 見て意味が分かる短い値は即値にし、GUID・長い時刻等の読めないサンプルには名前を付ける。単なる `actual`・`result` への代入は不要で、対象を受ける意味があり型名を言い換えるだけなら `tested` とする。
- 実時間待機、実行順序、個人の環境に依存させない。成功だけでなく要求された失敗表示や境界状態を確認する。削除が要件のデモ要素も残存確認する。

## 検証

- `package.json`、lockfile、実在するscript、Nodeとパッケージマネージャーのバージョンを確認する。
- lockfileを維持し、採用済みのパッケージマネージャーで再現可能な導入方法を使う。npmと `package-lock.json` のプロジェクトなら通常 `npm ci` を使う。他のlockfileへ無断で切り替えない。
- パッケージを必要なく追加・更新・移動・削除しない。コード変更後は対象・関連テストと、実在するlint・test・buildのscriptを実行する。
- proxy変更は可能なら実起動で疎通を確認する。IDE起動統合はCLI検証と区別し、実操作していなければ未確認と報告する。
